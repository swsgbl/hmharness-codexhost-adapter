## 0.10.0 Migration

`scripts/apply-codexhost-0.10.0.mjs` performs the runtime integration:

- Adds the controller and renderer HMHarness agent/model/ownership mappings using exact patch anchors.
- Installs the sole verified plugin under `~/.codexhost/plugins/hmharness` and removes the installer-directory duplicate.
- Embeds the dedicated HMHarness SVG in the renderer.
- Installs the request-bridge warmup retry and plugin-thread ownership paths.
- Forces the two Statsig feature gates and layer `72216192` used by the Chinese locale path.
- Restores the Chrome extension host config and Native Messaging wrapper.

The important 0.10.0 i18n fix is in `withRendererI18nGate()`. Earlier logic searched for the first `(() => {` substring; because the inserted patch itself contains `setInterval(() => {`, a repeated migration could copy a growing block of the previous patch. The 0.10.0 script now anchors on:

```text
(() => {
  var __defProp = Object.defineProperty;
```

and accepts one optional newline between the patch and the original app bundle. Repeated applications completed successfully and preserved:


## ChatGPT Chrome Extension

Installed extension:

```text
ID: hehggadaopoacecdllhhajmbjkdcmajg
Version: 1.26.901.11451
Side panel: codex-sidepanel/index.html
```

The extension-host config points to:

- Current Chrome plugin root: `~/.codex/plugins/cache/openai-bundled/chrome/latest`.
- Current Desktop app-server CLI: `~/.codex/plugins/.plugin-appserver/codex.exe`.
- Current `cua_node` runtime.

Official checks returned `correct: true` for both:

```text
scripts/check-native-host-manifest.js --browser chrome --json
scripts/check-native-host-manifest.js --browser edge --json
```

The Native Messaging manifest now points to:

```text
C:\Users\hongfu\.codex\extension-host-no-codexhost.cmd
```

The wrapper clears `CODEX_CLI_PATH` and `CODEXHOST_STOCK_CODEX_PATH`, then launches the official extension host. Re-running the 0.10.0 migration restored this wrapper after a later official installer/repair step had overwritten the manifest back to the direct executable.

Chrome 153 ignores the legacy `--load-extension` flag, so the isolated test used CDP `Extensions.loadUnpacked`. The extension loaded with the exact ID. Directly opening a protected side-panel URL in a normal tab returns `ERR_BLOCKED_BY_CLIENT`; this is Chrome resource protection, not an extension failure. A temporary copy added `codex-sidepanel/*` to `web_accessible_resources` only for the isolated smoke test. The user's installed extension was not modified.

The isolated page rendered:

```text
ChatGPT is ready
Open the ChatGPT side panel to start the local app server
```

with no page exception. After an isolated Chrome cold restart, the exact process chain was:

```text
isolated chrome.exe
  -> cmd.exe /c C:\Users\hongfu\.codex\extension-host-no-codexhost.cmd ...
     -> extension-host.exe chrome-extension://hehggadaopoacecdllhhajmbjkdcmajg/ ...
```

The existing user Chrome process had already cached the older direct-host manifest at startup. It was not killed. That Chrome must be fully restarted by the user before its extension will use the repaired wrapper.
