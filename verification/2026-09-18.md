# CodexHost 0.9.0 HMHarness validation

Date: 2026-09-18, Asia/Shanghai.

## Scope

- Upgrade to the official CodexHost `0.9.0` Windows installer distribution.
- Adapt HMHarness to the 0.9.0 controller/renderer arrays, including the new `qoder` and `qoder-cn` agents.
- Preserve the same plugin bytes and dedicated HMHarness icon.
- Verify model selection, a real UI request, final UI cleanup, bridge cleanup, Windows shutdown restoration, and a cold relaunch.

## Functional Evidence

- The migration script passed syntax validation and two consecutive applies.
- The Windows placement helper moved the plugin to `~/.codexhost/plugins/hmharness`, enabled that copy, removed the installer-directory duplicate, and verified both SHA-256 values.
- The renderer reported `enabledAgents` including `hmharness`, `availability.hmharness=ready`, adapter `state=ready`, and `modelUpdates=1`.
- The live agent menu exposed `HMHarness`; the mounted composer selected it and displayed/selected `glm / glm-5.3`.
- The HMHarness menu option rendered the bundled base64 SVG. Its complete `img src` matched the local `icon.svg` base64 encoding and did not use the Antigravity fallback.
- A real composer turn sent exact marker `HMH_CODEXHOST_090_20260918_OK`.
- `run_20260917175050_9b4a0c` completed in 25.324 seconds with `model=glm-5.3`, `outcome.success=true`, and `outcome.reason=final`.
- After the response, the composer was empty, the visible `正在思考` count was `0`, and no `hm-codexhost` bridge process remained.
- CC Switch on `127.0.0.1:15721`, codex-image-proxy on `127.0.0.1:15731`, and the existing DSH Web listener were not stopped.

## Shutdown And Relaunch

After the marker turn, only the Codex Desktop processes were closed. The Host shim exited with them. After roughly 5.5 seconds, the launcher removed `windows-090-launch-fallback.json`, restored the original HKCU values, and left no CodexHost shim entry in `~/.codex/config.toml`.

A cold launch through `Desktop\CodexHost.lnk` returned Desktop, CodexHost, and the shim to a running state. HMHarness was again `ready` and selected, with `glm / glm-5.3` and the same dedicated icon. The CDP listener changed from `59340` to `63623`; future diagnostics must discover the current listener rather than assume a fixed port.

```powershell
node scripts/apply-codexhost-0.9.0.mjs
node scripts/apply-codexhost-0.9.0.mjs  # idempotency
pwsh -NoProfile -ExecutionPolicy Bypass -File tools/install-windows.ps1

```

Launch through `Desktop\CodexHost.lnk`, discover the current ChatGPT CDP listener, select HMHarness and `glm / glm-5.3`, send one unique marker, then verify the run summary, empty composer, Thinking count `0`, no bridge child process, dedicated icon, and shutdown restoration.
