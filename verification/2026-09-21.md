# Codex Host 0.9.1 Chinese UI and HMHarness duplicate-plugin regression

Date: 2026-09-21, Asia/Shanghai.

## Scope

- Preserve the working Codex Host `0.9.1`, Codex CLI `0.155.1`, and Codex Desktop `26.915.4065.0` upgrade from 2026-09-20.
- Make the visible Codex Desktop UI honor the configured `zh-CN` locale.
- Prevent the 0.9.1 migration from creating two plugins with `id=hmharness`.
- Re-run the HMHarness desktop regression and add visible Chinese UI to the mandatory upgrade gate.

## Chinese UI Root Cause

The usual settings and resources were already correct:

- `~/.codex/config.toml` had `localeOverride = "zh-CN"`.
- The Chromium renderer launched with `navigator.language=zh-CN`.
- The Codex Desktop distribution contained the `zh-CN` message bundle.

The remaining gate was the official Statsig layer `72216192`. At runtime it returned:

- `enable_i18n=false`
- `locale_source` did not resolve to the IDE locale

With that gate disabled, React used the default English messages even though the Chinese resource files existed. Earlier upgrade checks stopped at configuration and resource presence, so this was missed. Visible localized UI is now a mandatory acceptance condition.

`scripts/apply-codexhost-0.9.1.mjs` now installs a renderer preload patch before the app bundle starts. The patch polls for the Statsig namespace because `firstInstance` can be assigned before its `getLayer` method exists. Once available, the client is patched idempotently so layer `72216192` returns:

- `enable_i18n=true`
- `locale_source="IDE"`

The replacement logic is also idempotent, so reapplying the migration replaces an older i18n patch instead of stacking patches.

## Duplicate HMHarness Plugin Root Cause

After migration, HMHarness briefly returned:

```text
Harness 'hmharness' is unavailable
```

The renderer status exposed a duplicate plugin id: the migration had copied HMHarness into the Codex Host app plugin directory, while the Windows placement helper also installed it under `~/.codexhost/plugins/hmharness`. Codex Host `0.9.1` rejects duplicate plugin ids, so both copies could be excluded from the agent list.

The 0.9.1 migration now automatically invokes `tools/install-windows.ps1` on Windows after patching the runtime. The final state is:

- App plugin directory: no `hmharness` directory and no `hmharness` entry in its `enabled.json`.
- User plugin directory: the sole `hmharness` directory and its enabled entry.
- Plugin `plugin.mjs` SHA-256: `57D1EDD1394F2011B0FF4C88830870FF64C6D4A0A49BFA3BAF5C7094FDA4436A`.
- Icon SHA-256: `950FA9B06484F9D56C51A976679252D3061832279292658C20E59D9F06FE75DF`.

A repeated `node scripts/apply-codexhost-0.9.1.mjs` completed successfully, rebuilt the renderer/controller patches, and reported the same archived hashes.

- The composer selection was `agent=hmharness`, `phase=locked`.

The final visible Thinking count was `0`, and no residual `hmh-codexhost` process remained after the turn.

## Future Upgrade Gate

Every future Codex Host/Codex Desktop adaptation must pass all of the following before it is reported as complete:

1. A cold launch through the real desktop shortcut and a dynamically discovered CDP port.
2. Visible Chinese menu labels plus `IntlProvider(locale=zh-CN)` with a non-empty Chinese message catalog.
3. The Statsig patch marker and `enable_i18n=true`.
4. Exactly one enabled HMHarness plugin installation.
5. `availability.hmharness="ready"` and a locked HMHarness selection.
6. A real marker turn through the composer with the expected model.
7. Final Thinking count `0` and no residual `hmh-codexhost` process.
8. The same committed adapter HEAD pushed to both GitHub and AtomGit.

No pull request is submitted to `BytePioneer-AI/codex-host`; the maintainers have declined HMHarness support. This repository remains the user-owned backup implementation.
